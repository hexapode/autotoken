Autotoken watches model traffic for repeated work, tries writing a program for it, and tests that program on new tasks. A decision model routes future requests to tested code or the main model. Each outcome feeds the next round of learning.

01 / Install and try it

Run the proxy
on your machine.

You need Node.js 22.19 or later. Install from GitHub, then try the offline demo without an API key. Docker and Pi are not required.

The proxy records traffic. Installing it does not turn on automatic model-call replacement. Live requests use your provider account and its normal charges.

Install from GitHub
npm install -g github:hexapode/autotoken
autotoken demo

The demo uses fixed examples to show the idea. It does not call a model or measure real savings.

1 / Configure and start
autotoken init
# Edit .autotoken.env:
# set LLM_API_KEY to your provider key

autotoken proxy --provider openai

init creates a local configuration file with a random PROXY_TOKEN and adds the config and recording directory to .gitignore. Keep your provider key in that local file.

2 / Point your client at the proxy
Base URL: http://127.0.0.1:3001/v1
API key:  your local PROXY_TOKEN
Model:    your usual provider model ID

Use the token from .autotoken.env as the client’s API key. The proxy uses your provider key upstream. Keep the client’s existing model choice and API format.

Anthropic, compatible providers, and Ollama

Use the provider’s native API format; the proxy does not translate between APIs.

# Anthropic (LLM_API_KEY or ANTHROPIC_API_KEY)
autotoken proxy --provider anthropic
# Anthropic SDK base URL: http://127.0.0.1:3001
# The SDK appends /v1/messages.

# OpenAI-compatible provider
autotoken proxy --provider compatible --upstream https://YOUR_PROVIDER/v1

# Local Ollama
autotoken proxy --provider ollama

Chat Completions, Responses, and Anthropic Messages are supported. The model ID remains your client’s choice. See the README for setup details and the coding experiment guide for Pi and repository tests.

↳ The hypothesis

We want to use models to find repeated work and write programs for it. Then we need to check whether those programs work on new requests.

02 / The learning loop we want to build

Spot a pattern.
Write, test, route, repeat.

The system learns two things: how to do a recurring task with code, and when that code applies. We now have recording, a restricted program compiler, a shadow decision API, and a first router trained on traces. Reliable automatic deployment is still the goal.

01 — RECORD

Collect real work

The proxy records requests, context, tool actions, outcomes, and usage while the model does the job.

02 — SPOT A PATTERN

Find a recurring task

Compare traces for repeated procedures across different inputs. A sequence of routine checks may be more useful than one repeated command.

03 — WRITE CODE

Try a small program

A model writes a candidate with defined inputs, outputs, and conditions for use. For example: collect the patch, check whitespace, and report repository status.

04 — TEST

Make it earn traffic

Test edge cases and new issues. Run it alongside the normal path in an isolated copy, then compare task outcomes, cost, and time. Reject programs that do not help.

05 — ROUTE

Choose a program or model

A decision model sees the request and eligible programs. It returns a program ID and arguments, or falls back to the main model. Code checks the arguments and conditions before execution.

06 — LEARN

Use the outcome

Record whether the choice worked and what it cost. Use verified outcomes to improve programs and the router. Keep checking new versions on separate examples before promoting them.

↶

Every outcome becomes another example. Failures suggest missing conditions or new tasks to automate. Successful matches teach the router when a program fits. A program can also be retired when it stops helping.

Start with a decision API

A small choice, with a fallback.

One endpoint receives the request, relevant context, and a shortlist of tested programs. It returns a structured choice. A model API can make this decision first; a local classifier can later serve the same interface.

{ "route": "program", "program": "patch_review_v1",
  "arguments": { "scope": "current_patch" } }

{ "route": "model" }

The router chooses from a registry. It does not invent executable commands. Invalid arguments, unmet conditions, or failed checks return control to the main model.

Then improve the decision

Learning does not require a fine-tune on every request.

Start by updating the program catalog and adding verified examples to the router’s prompt. Once we have enough labeled outcomes, train a small classifier and compare it with the API router.

The prototype can update a candidate classifier after each labeled replay outcome; the serving policy stays frozen. A candidate router still needs evaluation before replacing the active version. A model’s confidence or a command exiting successfully is not proof that the task was solved.

Measure the full bill: routing, program execution, fallback, discovery, and evaluation. A router only helps if those costs are lower at comparable task quality.

Replay estimate · 300 trajectories

How many turns could code replace?

We checked four programs against 11,525 recorded assistant turns. There are 34 exact, command-only matches (0.30% of turns). Including equivalent reads and assuming accompanying reasoning can be omitted gives 572 potential replacements (4.96%).

The broader scenario includes 469 write-and-run steps, 61 navigation steps and 42 read repairs. Automatic script execution would require explicit opt-in. These are opportunities in discovery traces, not demonstrated saved calls.

Most of that is context that would not need to be sent for a skipped request. This assumes full conversation history on each request. Actual usage, context truncation, caching and routing costs are unavailable; these are gross estimates, not billed savings.

We found ten comparison turns across six discovery issues. The program puts identical regression tests in separate original and patched copies. A synthetic bug fails before the fix and passes afterward, while the source worktree stays unchanged. Historical test overlays have not been reconstructed, and no saved calls are established.

Compact reads · smaller tool arguments

A tuple-based read operation used 24.9% fewer argument bytes across 24 supported discovery turns: 2,589 → 1,945 bytes. That is 644 bytes total. The model still chooses what to read; tool-schema costs, output overhead, and token savings have not been measured. Nine fixture checks pass.

Find related tests · lightweight filename hints

Using only previously mentioned source files and the original repository tree, a program suggested test filenames on 61 turns. On fifteen of those turns, a suggestion matched a file requested next. The hints total 2,343 bytes, but they do not replace reading tests or deciding what to change. Thirteen fixture checks pass.

Failure traceback context · low priority

Returning source around traceback locations produced 28 bounded plans, but covered no complete following turn in the discovery traces. Those plans could add up to 2,720 lines of context. The planner passes its checks; the evidence does not support automatic injection yet.

What we ruled out in the earlier local sample

Strict replay found no duplicate read ranges to remove. An audit of 140 Python snippets found only two unrelated inspection examples, too little for a reusable helper. A failed-test planner produced 22 proposals, but none matched the next recorded test selection. These checks found no additional savings in the local sample. Approach

In each run, the coding agent had to fix a real bug in a fresh repository checkout. The approaches below change how it checks its patch.

Astroid: keep the code analyzer from crashing

Astroid examines Python code to infer what values expressions might produce. An expression such as "{:d}".format(None) made the analyzer itself crash.

A correct fix: handle formatting it cannot infer without crashing. Python’s formatting rules stay the same.

Our check: analyze two invalid formatting expressions without raising an exception, then run the repository tests.

pydicom: export valid data despite an invalid field

pydicom converts medical-image metadata to JSON. A malformed integer field could stop the export even with suppress_invalid_tags=True.

A correct fix: let export finish with suppression enabled and preserve valid fields. Without suppression, the error should still surface.

Our check: export a dataset containing an invalid integer and a valid patient-name field, then run the repository tests.

What we changed

After a test command passes and the repository has changes, a fixed rule runs either git diff --check or the full suite plus diff checks and statistics. The agent receives those results with its tool output. If a check fails or cannot finish, the model gets the result and continues.

We chose this rule ourselves and added it to the tool executor. A learned model did not select it. The normal proxy still records requests without replacing model calls.

04 / State of the project

What works today,
and what we are still testing.

The sorting prototype and coding experiment test different parts of the idea. A result in one does not show that the other works.

IMPLEMENTED

Small data tasks

The first prototype can propose and route to small programs for tasks such as sorting. Programs must pass tests and checks on new inputs before activation. The demo uses fixed examples, not live models.

SHADOW PROTOTYPE

A router that can learn

The decision API can use a model or a local classifier. Recorded outcomes can train a candidate router while the current policy stays unchanged. Automatic activation is still under development.

RESEARCH

Automatic test commands

Coding experiments explore whether a short program can handle routine verification steps. We compare it with the usual agent workflow on separate issues.

Could the decision model learn as requests arrive?

Yes. A small online classifier could learn which program applies from verified examples. A contextual bandit could learn which eligible route gives the best outcome and cost. It observes only the route actually taken, so we also need held-out tests and controlled comparisons; missing outcomes are not evidence that another route would fail. The prototype now supports incremental classifier updates from replay labels. A contextual-bandit policy and automatic deployment are not implemented. How contextual bandits work ↗

Do we need a special decision API?

No specific service is required. We can put an ordinary model API behind our own routing endpoint and request a structured program choice. Structured output makes the result parseable; our tests and runtime checks still decide which programs are eligible. Example: structured outputs with Claude ↗

Is this just a response cache?

The goal is to reuse a procedure across new inputs, rather than replay an answer to a previous request. A sorting program can handle an array it has never seen. Its applicability still needs to be checked.

Does it eliminate model calls?

An active program can avoid an answer-model call, but the decision model still uses inference. Discovery and shadow evaluation add costs too. The small paired workflow trial used fewer model queries than baseline, but its fixed rule is not a learned router. General net savings have not been established.

Can generated code run anything it wants?

No. The data prototype can only use a small set of operations, such as sorting and counting. Coding-task proposals select from a fixed list of read-only commands. The workflow experiment runs a configured test suite and diff checks. The coding agent itself can still run local commands; local execution is not a sandbox.

What would count as a convincing result?

We would need to fix the programs before testing them on new tasks, repeat both the ordinary and modified runs, and preserve task success. We would also need lower total cost or time after counting the work of discovering programs and deciding when to use them.
