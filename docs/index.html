↳ The hypothesis

A model can help discover a procedure once. A program can repeat that procedure many times. The hard part is knowing when it applies.

01 / The learning loop

From observed work
to reusable behavior.

Start with traffic instead of a hand-written catalog of tasks. Let evidence determine what is common enough—and precise enough—to automate.

01 — OBSERVE

Watch the work

A proxy records requests, responses, tool actions, and results while the model keeps doing the job.

02 — DISCOVER

Find repetition

A learner looks across distinct examples for recurring intent and a procedure that could generalize.

03 — VALIDATE

Make it explicit

Build a bounded program with an input contract. Test it, then compare it in shadow mode on new inputs.

04 — ROUTE

Use it selectively

A decision model selects an eligible program or abstains. Rejections and execution errors fall back to the answer model.

What the intervention actually does

After successful tests on a changed checkout, a fixed rule runs either git diff --check or the full suite plus diff checks and statistics. The agent receives those results with its tool output. Failed or inconclusive checks fall back.

This tests a bounded workflow in the tool executor. It is not yet the learned decision-model router in the proposed architecture. Ordinary traffic collection remains record-only.

EXPERIMENT IN PROGRESS

Does the result repeat?

The initial result supports further testing, not automatic promotion. A larger experiment is running: six new issues, two rollouts, and three arms—36 planned runs. Its results will be reported separately.

We are keeping issue splits, fresh checkouts, available independent regressions, and model overhead visible as the experiment grows.

03 / State of the project

A working prototype.
An open research question.

The small data-transformation prototype and the coding-agent experiment are separate paths. Their evidence should be read separately, too.

IMPLEMENTED

Bounded transformations

A model router, a small operation language, candidate tests, shadow comparison, explicit promotion, and fallback. The bundled demo uses scripted fixtures.

IMPLEMENTED

Agent observation

Pi integration, streaming trace capture, patch export, local issue validation, and cross-run analysis. Offline discovery and held-out replay help identify candidate substeps; ordinary collection stays record-only.

EARLY LIVE EVIDENCE

Bounded workflows

A fixed validation rule has completed a six-run paired trial. Broader repeated evaluation is next; learned agent routing and general savings remain unproven.

Is this just a response cache?

The goal is to reuse a procedure across new inputs, rather than replay an answer to a previous request. A sorting program can handle an array it has never seen. Its applicability still needs to be checked.

Does it eliminate model calls?

An active program can avoid an answer-model call, but the decision model still uses inference. Discovery and shadow evaluation add costs too. The small paired workflow trial used fewer model queries than baseline, but its fixed rule is not a learned router. General net savings have not been established.

Can the learner execute arbitrary generated code?

The transformation prototype uses a bounded JSON operation language. The offline agent proposal compiler selects from a fixed set of read-only operations. A separate experimental tool executor can run a configured test suite and bounded diff checks. Neither path enables arbitrary learner-generated source in live routing. The coding agent's local execution mode itself is not sandboxed.

What would count as a convincing result?

A frozen registry evaluated on unseen issues, with paired baseline and routed runs, stable task success, and lower total cost or latency after including routing and learning overhead. Discovery, calibration, and test issues must stay separate.
