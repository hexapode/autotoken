The hypothesis

A model can help discover a procedure once. A program can repeat that procedure many times. The hard part is knowing when it applies.

01 / The learning loop

From observed work
to reusable behavior.

Start with traffic instead of a hand-written catalog of tasks. Let evidence determine what is common enough—and precise enough—to automate.

01 — OBSERVE

Watch the work

A proxy records requests, responses, tool actions, and results while the model keeps doing the job.

02 — DISCOVER

Find repetition

A learner looks across distinct examples for recurring intent and a procedure that could generalize.

03 — VALIDATE

Make it explicit

Build a bounded program with an input contract. Test it, then compare it in shadow mode on new inputs.

04 — ROUTE

Use it selectively

A decision model selects an eligible program or abstains. Rejections and execution errors fall back to the answer model.

A small, concrete example

Different words. The same operation.

“Sort these numbers.” “Put these values in ascending order.” A program can handle new arrays, provided the intent and input contract match.

The decision still requires care: “sort by absolute value” is a different task.

02 / First experiment

Can a coding agent teach us
which steps repeat?

Put the proxy between Pi and the model. Run real repository issues. Study the decisions inside each trajectory.

Pi coding agent→Autotoken proxy→gpt-6.1-sol
2distinct development issues
17recorded model calls
2 / 2passed local validation

Pilot snapshot: two marshmallow issues from SWE-bench Lite's development split. Patches passed repository tests and independent public-issue regressions in fresh checkouts. These are local checks, not official SWE-bench scores. All 17 calls still went to the model.

What we observed

Both trajectories include workspace inspection, file reading, searching, editing, testing, and diff review. The analyzer counts current actions, links tool results, and separates distinct issues from repeated runs.

What that does—and does not—tell us

Recurring categories suggest places to investigate. They do not establish that an entire model decision is replaceable. We still need held-out shadow evaluation and paired agent runs to measure downstream correctness and net savings.

03 / State of the project

A working prototype.
An open research question.

The small data-transformation prototype and the coding-agent experiment are separate paths. Their evidence should be read separately, too.

IMPLEMENTED

Bounded transformations

A model router, a small operation language, candidate tests, shadow comparison, explicit promotion, and fallback. The bundled demo uses scripted fixtures.

IMPLEMENTED

Agent observation

Pi integration, streaming trace capture, patch export, local issue validation, and cross-run analysis. Two bounded action proposals remain offline and inactive; neither exactly replaces a full observed command.

NEXT TO VALIDATE

Agent substitution

Freeze candidates, test on unseen issues, then compare baseline and routed runs. Measure patch quality alongside coverage, latency, and all model costs.

Is this just a response cache?

The goal is to reuse a procedure across new inputs, rather than replay an answer to a previous request. A sorting program can handle an array it has never seen. Its applicability still needs to be checked.

Does it eliminate model calls?

An active program can avoid an answer-model call, but the decision model still uses inference. Discovery and shadow evaluation add costs too. The coding-agent path currently substitutes no calls, and the project has not demonstrated net cost savings.

Can the learner execute arbitrary generated code?

The transformation prototype uses a bounded JSON operation language. The offline agent proposal compiler selects from a fixed set of read-only operations. Proposed agent programs are not connected to live routing. The coding agent's local execution mode itself is not sandboxed.

What would count as a convincing result?

A frozen registry evaluated on unseen issues, with paired baseline and routed runs, stable task success, and lower total cost or latency after including routing and learning overhead. Discovery, calibration, and test issues must stay separate.
